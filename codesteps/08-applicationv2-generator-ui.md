# Step 08 — ApplicationV2 Generator UI

**Status:** 🔄 In progress — code complete, awaiting manual in-Foundry verification
**Milestone:** v0.1 — Skeleton
**Depends on:** [07](07-foundry-module-bootstrap.md)

## Goal

Give the engine a face: pick a pack, pick a variant, generate, copy the result. Built on `ApplicationV2` + `HandlebarsApplicationMixin` — the current Foundry pattern, not the deprecated `FormApplication`.

## Deliverables

- `src/apps/GeneratorApp.ts` — `ApplicationV2` + `HandlebarsApplicationMixin`
- `templates/generator.hbs`
- Launch point: `src/module/launchPoint.ts` — a Journal Directory header button (via `Hooks.on("renderJournalDirectory", ...)`) plus a minimal `game.modules.get("onomasticon").api.openGenerator()` for macros (a stepping stone; step 14 formalizes the real public API)
- **Not originally scoped, but required for the UI to generate anything real inside Foundry** (see below): `src/generateWithRegistry.ts`, `src/browser/loadBundledRegistry.ts`, `src/module/constants.ts`, `scripts/generateManifest.mjs` + `data-manifest.json`
- Also not originally scoped, found necessary during manual testing: `styles/onomasticon.css` (registered via `module.json`'s `"styles"` array)

## Key decisions

- **Closed a real gap steps 03/06 had deferred with hand-waving**: `generate()` was Node-only (`registry.ts` uses `node:fs`), but the UI needs to generate names inside a _browser_. Fixed by:
  - Extracting the registry-agnostic core out of `generate.ts` into `src/generateWithRegistry.ts` (zero Node imports) — both `registry.ts` (Node/`fs`) and `browser/loadBundledRegistry.ts` (fetch) produce the same `Registry` shape (now defined in `data/types.ts`, shared by both), and `generateWithRegistry(packId, options, registry)` doesn't care which one it was given.
  - `browser/loadBundledRegistry.ts` fetches a small `data-manifest.json` (id -> filename for every bundled pack/lexicon, generated by `scripts/generateManifest.mjs` so it can never drift out of sync — wired into `npm run build`), then fetches each listed file and validates it through the _exact same_ environment-agnostic validators from step 03 (`validatePackData`/`validateLexiconData` have no `fs` dependency, so they work identically in Node and browser). Nothing is fetched until the dialog actually opens — not at module `init` — honoring "lazy-load packs" without needing true per-lexicon-on-first-use staging, which isn't worth the complexity at the current scale (3 packs, 7 lexicons, ~20KB total).
  - **Caught by the build itself, not by review**: initially had `GeneratorApp.ts` import `generateWithRegistry` from `generate.ts`, which _also_ imports `registry.ts` in the same file — esbuild can't tree-shake away a same-file import that's actually used elsewhere in that file, so `node:fs`/`node:path`/`node:url` leaked straight into the browser bundle and `npm run build` failed outright with unresolvable-import errors. Fixed by importing from `generateWithRegistry.ts` directly, never through `generate.ts`. This is exactly the kind of mistake the "does it actually build clean" check exists to catch.
- Pack picker groups by each pack's first tag (`<optgroup>`); variant is a free-text input rather than a fixed dropdown, since variant is explicitly an open string (schema/pack.schema.json's own principle), not a closed enum.
- Per-slot reroll is a stretch goal, deferred — not implemented.
- **Fixed during manual testing:** the pack `<select>` and variant input reset to their defaults after every Generate click, because `_prepareContext` never fed the current selection back into the template across the re-render `#onGenerate` triggers. Fixed by tracking `#selectedPackId`/`#variant` as instance state (captured from the DOM right when Generate is clicked, same place the values were already being read) and reflecting them back in context — each `PackOption` now carries a `selectedAttr: "selected" | ""` computed in TS, and the variant input gets `value="{{variant}}"`. Note: a bare `{{#if}}...{{/if}}` block cannot appear inside an HTML tag's attribute list under Prettier's Handlebars (Glimmer-grammar) formatter — computing the whole attribute in TS and injecting it as a single mustache (`{{selectedAttr}}`) sidesteps that restriction.
- **Also fixed during manual testing:** with no stylesheet at all, the results list grew unbounded and older results scrolled out of the (auto-height) dialog with no way to reach them. Added `styles/onomasticon.css` (registered via `module.json`'s new `"styles"` array — the first use of that field) giving `.onomasticon-results` a fixed `max-height` and its own `overflow-y: auto`, so the dialog itself stays a fixed size and only the results list scrolls. That same pass regressed the `<ol>`'s native sequential numbering (`list-style: none` strips it) — the user relies on those numbers to point at a specific result when discussing the list with someone else. A first attempt restored it via `list-style: decimal`, but it still didn't render even after a full Foundry restart — Foundry's own base CSS almost certainly resets `list-style` on lists inside its window chrome with a more specific selector than a module stylesheet class can cleanly beat, so the fix landed but lost the cascade fight. Rather than escalate with `!important`, switched to rendering the number as real markup instead of relying on the browser's native counter: `GeneratorApp` now maps `#results` to `{ index, full }` pairs (`#resultEntries()`, 1-based, newest-first) and the template renders `<span class="index">{{this.index}}.</span>` explicitly — works regardless of what the host app's CSS does to list markers.
- `fvtt-types`' `ApplicationV2.RenderContext` uses TS's weak-type detection (optional-only base interface), so `GeneratorAppContext` explicitly `extends foundry.applications.api.ApplicationV2.RenderContext` to satisfy the override check on `_prepareContext`.
- Extended `src/test/foundryStubs.ts` with minimal `foundry.applications.api.{ApplicationV2,HandlebarsApplicationMixin}`, `game.modules`/`game.clipboard`, and `ui.notifications` stubs — enough that importing `GeneratorApp`/`launchPoint` doesn't crash under plain Node/vitest. These don't emulate real rendering; that's verified manually in Foundry, consistent with step 07's precedent.
- English strings are hardcoded for now (no `game.i18n.localize()` yet) — deliberate, per the plan: step 09 is the dedicated localization pass over this step's UI strings.
